\chapter{\uppercase{Design of Long Term Memory Engine for AI Agents}}
\label{ch:design}
This chapter describes the architecture and the five modules. For each module we show the data
it creates for one running example.

\section{\uppercase{The Maya Example}}
\label{sec:maya}
The example user, Maya, talks to the Pi agent in three sessions (Table~\ref{tab:maya-events}).
Each message is an \emph{event}, E1 to E5. She gives her city and job (E1), later says she has
moved (E3), and then asks a question that needs both (E5).

\begin{table}[H]
\caption{Events in the Maya example}
\label{tab:maya-events}

\begin{reporttable}
\begin{tabularx}{\textwidth}{|L{0.7cm}|L{1.4cm}|L{1.7cm}|L{1.9cm}|Y|}
\hline
\textbf{ID} & \textbf{Session} & \textbf{Role} & \textbf{Time (UTC)} & \textbf{Content} \\
\hline
E1 & S1 & user & 1 Oct, 04:30 & My name is Maya. I live in Chennai. I work as a software engineer at NovaTech, and I work remotely. \\
\hline
E2 & S1 & assistant & 1 Oct, 04:30 & Nice to meet you, Maya. \\
\hline
E3 & S2 & user & 10 Oct, 03:45 & I have moved to Bengaluru. Bengaluru is now my home city. \\
\hline
E4 & S2 & assistant & 10 Oct, 03:45 & Noted. You now live in Bengaluru. \\
\hline
E5 & S3 & user & 13 Oct, 06:00 & Where do I live now, where did I live before, and where do I work? \\
\hline

An agent that only kept E1 would wrongly say Chennai. The engine should know that Bengaluru
replaced Chennai on 10 October and still keep Chennai as her previous city. Real rows have
UUIDs; we use short names such as E3 and R2.

\section{\uppercase{Overall Architecture}}
Figure~\ref{fig:architecture} shows how the modules fit together. Pi's memory client saves
every message and asks for recall before answering. The service is written in Rust.
PostgreSQL with pgvector is the main store: events, chunks, assertions, quotes, vectors and the
job queue. Ollama runs our fine-tuned worker model and a Qwen3 embedding model. Neo4j keeps a
graph copy, and M4 checks every graph hit against PostgreSQL. M5 runs offline and never trains
on live chats.

Background work runs on Tokio workers so requests never wait. New events add a job to a queue
table. Four inference workers run M2 jobs and one projection worker runs M3 graph jobs. A
failed job is retried up to five times. A worker holds a 15-minute \emph{lease} (a temporary
lock) on the user's namespace, so two workers never change the same memory at once.

\section{\uppercase{M1 Source Acquisition and Processing}}
\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth,height=0.66\textheight,keepaspectratio]{figures/fig3_2_module1.png}
\caption{Module 1: Source Acquisition and Processing}
\label{fig:m1}

M1 saves the events before any model runs (Figure~\ref{fig:m1}). Pi writes each batch to a
local spool file, then sends it to \code{POST /api/v2/retain} with an idempotency key,
\code{external\_id}, so retries don't create duplicates. The events, their \emph{chunks}
(searchable copies with a keyword index and a vector) and an extraction job are saved in one
transaction. A failed model call later can't lose a conversation.

\section{\uppercase{M2 Knowledge Extraction and Consolidation}}
\label{sec:m2-design}
M2 has two stages, both run by our local model (Figure~\ref{fig:m2}). In \emph{extraction},
the model reads the new events and related stored assertions and returns \emph{claims}, each
with an exact quote. Bad output is retried up to two more times, and claims containing secrets
are dropped. In \emph{consolidation}, the model combines two or more active assertions about
one subject into an \emph{inference}.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth,height=0.66\textheight,keepaspectratio]{figures/fig3_3_module2.png}
\caption{Module 2: Knowledge Extraction and Consolidation}
\label{fig:m2}
\end{figure}

\begin{maya}[Maya example: what M2 extracts]
The model sees Maya's stored assertions, such as R1 (home city Chennai), and the events E3
and E4. It returns (some fields left out):
\begin{datablock}
{ "claims": [ {
    "subject": { "name": "Maya", "entity_type": "person" },
    "predicate": "home city",   "value": "Bengaluru",
    "statement": "Maya's home city is Bengaluru.",
    "cardinality": "single",    "kind": "fact",
    "confidence": 0.95,         "correction": true,
    "valid_from": "2026-10-10T03:45:00Z",
    "source_indices": [0],
    "quotes": ["Bengaluru is now my home city."] } ] }
\end{datablock}
The quote is an exact substring of E3, and \code{correction: true} marks a replaced value.
Consolidation later combines her work assertions A1 to A3:
\begin{datablock}
{ "observations": [ {
    "statement": "Maya works remotely as a software
                  engineer at NovaTech.",
    "confidence": 0.8,
    "supports": ["A1", "A2", "A3"] } ] }
\end{datablock}
\end{maya}

\section{\uppercase{M3 Temporal Knowledge and Graph Management}}
M3 is the only module that writes assertions, inside one locked transaction
(Figure~\ref{fig:m3}). It finds the entity and compares the claim with the \emph{slot}
(subject plus predicate). A repeated value gains a source; an empty slot gets a new assertion.
A different value supersedes the old one only if the claim is a correction with confidence at
least 0.8; otherwise both are marked contested. Old values are never deleted. The projection
worker then copies the change to Neo4j \cite{neo4j2026http}, using revision numbers so an old
change never overwrites a newer one.

\centering
\includegraphics[width=\textwidth,height=0.66\textheight,keepaspectratio]{figures/fig3_4_module3.png}
\caption{Module 3: Temporal Knowledge and Graph Management}
\label{fig:m3}
\end{figure}

\begin{maya}[Maya example: how M3 stores the move]
The slot \code{Maya::home city} holds R1 (Chennai). The new value differs, the claim is a
correction and $0.95 \geq 0.8$, so R1 is superseded by R2 (Table~\ref{tab:m3-rows}).

Quotes and links are stored as:
\begin{datablock}
assertion_sources:  (R2, C3, "Bengaluru is now my home city.")
assertion_edges:    (R2 -> R1, supersedes)
                    (I1 -> A1, supports)
                    (I1 -> A2, supports)
                    (I1 -> A3, supports)
\end{datablock}
In Neo4j, R1 and R2 become \code{Assertion} nodes linked to a \code{KnowledgeEntity} node for Maya.
\end{maya}

\section{\uppercase{M4 Hybrid Retrieval and Grounded Reasoning}}
M4 answers recall requests (Figure~\ref{fig:m4}). The query runs keyword and vector search
over assertions and chunks, plus date search if it names a time. The top hits seed a Neo4j
expansion. Reciprocal Rank Fusion merges the lists, and the best results are packed into the
token budget with their quotes. An optional reflect endpoint writes a cited answer.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth,height=0.66\textheight,keepaspectratio]{figures/fig3_5_module4.png}
\caption{Module 4: Hybrid Retrieval and Grounded Reasoning}
\label{fig:m4}
\end{figure}

\begin{maya}[Maya example: the recall request for E5]
When Maya asks E5 on 13 October, Pi sends this request:
\begin{datablock}
{ "namespace": "user:maya",
  "query": "Where do I live now, where did I live before,
            and where do I work?",
  "top_k": 10, "max_tokens": 2048,
  "reference_date": "2026-10-13T06:00:00Z",
  "temporal": true, "include_raw": true }
\end{datablock}
Recall returns R2, I1, A1 to A3 and the text of E1 and E3. Superseded R1 is left out, but
the old city still reaches the agent through E1 (ranks in Section~\ref{sec:m4-impl}).
\end{maya}

\section{\uppercase{M5 Model Training and Evaluation}}
M5 runs offline and produces the worker model (Figure~\ref{fig:m5}). A generator writes short
episodes in 16 domains and a teacher model labels them. We train on the checked labels with
QLoRA, evaluate, and import the model into Ollama (details in Chapter~\ref{ch:results}). Each
training row pairs the same extraction prompt M2 builds with the expected claims, so the model
learns, for example, to mark Maya's move as a correction.
