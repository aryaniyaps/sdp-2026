\chapter{\uppercase{Design of Long Term Memory Engine for AI Agents}}
\label{ch:design}
This chapter describes the overall architecture and the five modules of the memory engine.
Each module is explained in general first and then shown on the Maya example.

\section{\uppercase{Overall Architecture}}
The memory engine is made of five modules:
\begin{enumerate}
  \item \textbf{M1 Source Acquisition and Processing} saves the raw conversation and queues the work.
  \item \textbf{M2 Knowledge Extraction and Consolidation} turns the saved text into assertions and combines related ones into inferences.
  \item \textbf{M3 Temporal Knowledge and Graph Management} stores the assertions with their history and copies them to the graph.
  \item \textbf{M4 Hybrid Retrieval and Grounded Reasoning} finds the right memory for a question and fits it into the model's budget.
  \item \textbf{M5 Model Training and Evaluation} produces the worker model that M2 and M4 use.
\end{enumerate}

Figure~\ref{fig:architecture} shows how they fit together. The client is the Pi coding agent. Its memory client
saves every message through the memory service and asks for recall before answering. The
service itself is a Rust application with API handlers and background workers. PostgreSQL
with pgvector is the main store for M1 to M4 and holds the source events and chunks,
entities, assertions, quotes, vectors and the job queue. Ollama runs our fine-tuned worker
model and a Qwen3 embedding model. Neo4j keeps a graph copy of the assertions and
entities, and M4 checks every graph hit against PostgreSQL again before using it. M5 runs
offline, and we do \emph{not} use live chats as training data.

\subsection{\uppercase{Tokio Workers}}
Tokio is the asynchronous runtime of the Rust service. A Tokio
worker is a background task started on that runtime (with \code{tokio::spawn}) inside the
service process. It does not belong to any request: it repeatedly takes a job from the
PostgreSQL queue, runs it and marks it done, or retries it later if it failed. Because Tokio
tasks are light, several can run at once without blocking the API. The service starts a
pool of inference workers (4 by default, set between 1 and 8) that handle the extract and
consolidate jobs of M2, and one projection worker that handles the graph jobs of M3
(project, rebuild and clear). A lease on the namespace stops two workers from processing the
same namespace at the same time.

\section{\uppercase{M1 Source Acquisition and Processing}}
M1 saves the source events before anything else (Figure~\ref{fig:m1}). The client first writes
each batch to a local spool, so nothing is lost if the service is down, and then sends it to
\code{POST /api/v2/retain}. If the same key comes again with the same hash, the service just
returns the existing IDs, so retries don't create duplicates. The episode, events, chunks and
a pending extraction job are saved in one transaction, and each chunk gets a 1,024-dimensional
vector. Saving happens \emph{before} extraction, and extraction runs later as a queued job, so a
failed model call can't lose a conversation. Tokio workers lease a namespace for 15 minutes
and try a job up to 5 times.

\section{\uppercase{M2 Knowledge Extraction and Consolidation}}
M2 has two stages and both use our local model through Ollama (Figure~\ref{fig:m2}). In
extraction, the prompt builder fits the new events and the relevant existing assertions into
the model's input (Section~\ref{sec:alg-context}), and the model returns claims, each with an
exact quote from the source. If the output breaks the schema or quotes text that isn't in the
source, we ask again, up to two more times. Secrets are filtered out before the claim goes to
M3. In consolidation, after M3 commits, the model can combine two or more active assertions
about the same subject into one inference.

\section{\uppercase{M3 Temporal Knowledge and Graph Management}}
M3 is the only module that writes assertions. It works inside one PostgreSQL transaction
that holds a namespace lock (Figure~\ref{fig:m3}). First it finds the entity. If the same value
is already stored, it is reinforced, and if the slot is empty, a new assertion is made. If a
single-valued slot gets a different value, the old assertion is superseded when the claim is a
reviewed correction with confidence of at least 0.8; otherwise both are marked contested. When
an assertion changes we add a new version and keep the old value with its validity interval.
The projection worker then copies the change to Neo4j \cite{neo4j2026http}. It checks revision
numbers so an old revision can't overwrite a newer one.

\section{\uppercase{M4 Hybrid Retrieval and Grounded Reasoning}}
M4 answers recall requests (Figure~\ref{fig:m4}). A request carries the namespace, a
\code{top\_k}, a maximum distance and a token budget. The query goes to keyword search, vector
search and, if there is a date window, time-based search. The top results are the starting
points for a Neo4j expansion. All the lists are merged with Reciprocal Rank Fusion and packed
into the budget along with their source quotes. There is also an optional reflect endpoint
that writes an answer with citations.

\section{\uppercase{M5 Model Training and Evaluation}}
M5 runs offline and produces the worker model that M2 and M4 use (Figure~\ref{fig:m5}). A
generator makes short episodes across 16 domains and a teacher model labels them. We train
the model on the checked labels with QLoRA, evaluate it and import it into Ollama (details in
Chapter~\ref{ch:results}).
