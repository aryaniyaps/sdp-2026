\chapter{\uppercase{Results, Performance Analysis and Comparison}}
\label{ch:results}
This chapter describes the training data and the fine-tuned model, shows the engine in a live session, and then
measures it. The measurement asks one question: does an agent answer questions about a long conversation better
with the memory engine than without it, and at what cost? It ends with a comparison against published memory
systems and the limits of what the results show.

\section{\uppercase{Datasets}}
Each training row has the same shape: the input is a short conversation plus a task
(extract, consolidate or reflect), and the output is the expected memory, i.e. assertions,
inferences or an answer, each tied to a source quote. For example in the Maya
episode the user says ``I live in Chennai.'' and later ``Bengaluru is now my home city.'',
and the expected output is the assertion ``Maya, home city, Bengaluru'' with
\code{correction:true}, \code{source:user} and that quote. The training rows and prompts keep
the wording the model was trained on (kinds \code{fact} and \code{observation}, the heading
``Existing facts:''); the service translates these to \code{attribute} and \code{inference} at the
model boundary, so the renaming used in this report does not change the model's contract.

The fine-tuning data started out as only coding conversations and we later expanded
it to 16 domains (family, food, travel, education, work, software and so on). All
conversations are synthetic. They were generated by the teacher model GPT-5.6-sol,
cross-checked by a second adversarial model and then cleaned. In total there are 2,961
task examples, split into 2,095 for training, 424 for validation and 442 for testing.
Figure~\ref{fig:domains} shows the spread across domains. Software and technical projects is the
biggest with 240 rows and the rest have roughly 110 to 140 each. (Several tasks can come
from one episode, so this counts rows, not conversations.)

\begin{figure}[H]
\centering
\includegraphics[width=0.85\textwidth,height=0.26\textheight,keepaspectratio]{figures/fig5_1_domains.png}

A lot of the rows test whether the model keeps only what the user actually said. For
example, the assistant says ``You could learn violin this winter.'' and the user replies
``No, that is not my plan. I am learning watercolor painting.'' The expected memory is
just that the user is learning watercolor painting. The assistant's suggestion should not
become a memory.

The benchmark in Section~\ref{sec:setup} showed that this data asked for too few facts per conversation: most
episodes expected two or three claims, so the model learned to stop early. A third set was therefore generated for
coverage: 480 casual conversations between two people, each labelled with every durable fact it contains by
Claude Sonnet 5.5 as teacher (5,284 claims; 25 of the 480 labels failed validation and were dropped). Together
with 600 rows replayed from the earlier stages so that consolidation and answering were not forgotten, this gave
1,719 training and 670 validation rows. None of it uses LoCoMo text, so the benchmark below stays unseen.

\section{\uppercase{Fine-Tuning and Model Selection}}
The model is Qwen3-4B-Instruct-2507, fine-tuned with QLoRA \cite{dettmers2023qlora} and served
through Ollama. Following Figure~\ref{fig:m5}, GPT-5.6-sol labelled the episodes for the extract,
consolidate and reflect tasks, every label was checked for structure and source quotes (and
repaired if needed), and the valid ones were frozen into the 2,095/424/442 split. Rows
were tokenised with a 4,096 token limit and the prompt was masked so only the target
is supervised. Training used QLoRA on the frozen base with NF4 quantisation and rank
16, going from Stage A to Stage B. The adapter was then merged and quantised to a
Q8\_0 GGUF with llama.cpp, compared against the base model on 64 internal tasks and
16 external cases, checked live (retain, graph, recall/reflect), and packaged with a
SHA-256 checksum and imported into Ollama as \code{mem-extractor:general-v1}.

We actually started with Qwen3-1.7B. It was fine on synthetic examples but bad on
natural conversations, only 18 of 33 extraction windows passed validation even after
refinement. Most failures were wrong source attribution, quotes that didn't match and
invalid IDs. That's what pushed us to broaden the training data, tighten the output
constraints and move up to the 4B model.

Stage C continued from the Stage B adapter on the coverage set (one epoch, learning rate $3\times10^{-5}$, rank 16,
gradient accumulation 8). The limit per row was raised to 6,144 tokens because the new rows, which list every
fact, are longer. Training took 2.9 hours on the laptop's 8 GB RTX 4070 (peak memory 7.3 GB, checkpoints every 20
steps so that an out-of-memory crash resumes rather than restarts); the validation loss was 0.155. The result was
exported in the same way as \code{mem-extractor:general-v2}. Which worker to use for the test was decided by a
rule written before the comparison: \code{general-v2} replaces \code{general-v1} if its accuracy on the two
development conversations is at least as high. It was (Section~\ref{sec:iterations}).

\section{\uppercase{Experimental Setup}}
\label{sec:setup}
The benchmark asks one question: does an agent answer questions about a long conversation better with the
memory engine than without it, and at what cost? It uses LoCoMo \cite{maharana2024locomo}, the dataset on which
Mem0, Zep and A-Mem report their results \cite{chhikara2025mem0}. LoCoMo has ten long conversations between two
people, 272 sessions in all (about 16,000 tokens per conversation), and 1,540 questions with gold answers in four
categories: single-hop, multi-hop, temporal and open-domain. The 446 adversarial questions have no gold answer and
are left out, as in the Mem0 evaluation. Each conversation is retained into the engine as its own memory bank,
session by session in date order. Questions, answers and evidence labels are never ingested.

\subsection{Conditions}
Every question is answered by the same reader model with the same prompt under each condition in
Table~\ref{tab:conditions}; only the text the reader is given changes.

\begin{table}[H]
\caption{Benchmark conditions}
\label{tab:conditions}
\centering
\begin{reporttable}
\begin{tabularx}{\textwidth}{|l|Y|}
\hline
\textbf{Condition} & \multicolumn{1}{c|}{\textbf{What the reader is given}} \\
\hline
\code{enhanced} & The engine's recall: assertions with source quotes, inferences, graph neighbours and temporal planning, interleaved with source text, packed into 8,192 tokens \\
\hline
\code{raw\_hybrid} & Lexical and vector search over the raw source chunks only (plain retrieval-augmented generation), same budget \\
\hline
\code{recent\_window} & The newest 8,192 tokens of the conversation: what an agent without memory keeps when history overflows \\
\hline
\code{full\_context} & The whole conversation: an upper reference and the most expensive option \\
\hline
\code{no\_memory} & The question only \\
\hline
\code{assertions\_only}, \code{no\_graph}, \code{no\_consolidation} & \code{enhanced} without source text, the graph or inferences, on a 300-question sample stratified by category \\
\hline
\end{tabularx}
\end{reporttable}
\end{table}

\subsection{Reader, judges and metrics}
The reader is Claude Haiku 5.5, called through the Pi coding agent, with Mem0's single-store answer prompt plus one
line asking for the final answer as JSON. Two judges from different model families grade each answer against the
gold answer with Mem0's LoCoMo rubric, and never see which condition produced it: TypeSafe Jev \cite{typesafe2026jev}, a decision model
that returns the probability that the answer is correct (the primary judge, threshold 0.5), and GPT-4o-mini, called
exactly as in Mem0's released evaluation code so the numbers can be compared with published tables. Mem0's token F1
and BLEU-1 are computed without any model. Retrieval is scored against LoCoMo's evidence labels (the dialogue turns
that answer each question), and every source quote a recall returns is checked against the dataset turn it cites.

Differences are reported as paired bootstrap intervals \cite{efron1993bootstrap} (2,000 resamples), both over questions and over whole
conversations (a cluster bootstrap), because the questions about one conversation share one memory bank. Two extra
repetitions on the 300-question sample measure how much the reader's answers vary between runs. The agreement of the
two judges is reported as Cohen's kappa \cite{cohen1960kappa}.

\subsection{Protocol}
The conditions and success criteria were committed to the repository before the test run, and the run's manifest
records the commit together with a fingerprint of all code and configuration; a test run refuses to continue if
either changes. Faults were diagnosed only on two conversations (the dev split), and every change made because of
them is recorded with its before and after numbers. The test run uses all ten conversations with the final version,
and the eight conversations never used for diagnosis are also reported on their own.

\subsection{Reproducibility}
The benchmark is one command (\code{benchmark/overnight.sh}) on a single laptop with an 8 GB RTX 4070, and takes
about seven hours, most of it building memory. The dataset, the vendored Mem0 prompts and the fine-tuned model are
pinned by SHA-256. Every reader and judge call is stored with its full output and the hash of its prompt. The
\code{verify} command rebuilds each stored prompt from the stored retrieval and the pinned dataset and fails if any
stored answer has been changed; with \code{--live} it also re-asks the models on random items. The executed notebook
\code{Benchmark\_Report.ipynb} recomputes every number in this chapter from the stored records and prints random
items in full for checking by hand.

A separate property suite of 40 scripted conversations checks the behaviours claimed for the engine on its stored
state, without a judge: a knowledge update keeps the old value as history and \code{as\_of} recall returns it, a
relative day such as ``yesterday'' is resolved to a date, the engine abstains without evidence, a relative's move does
not overwrite the user's own city, and a credential is never stored.


\section{\uppercase{Development Iterations}}
\label{sec:iterations}
The first full runs on the two development conversations exposed faults in the engine, the extractor and the
benchmark harness. Each was diagnosed on those two conversations only, fixed, and recorded in
\code{benchmark/iterations.json} with the evidence before and after. Table~\ref{tab:iterations} summarises them.

Three further faults were in the harness rather than the engine: evidence labels used a different session name
from the one recall reports, so retrieval scored zero; an engine restart crashed the ingest stage instead of being
waited out; and the jobs API listed only the newest 100 jobs, which hid failed consolidations behind hundreds of
newer projection jobs. All three were fixed before the test run. Accuracies in Table~\ref{tab:iterations} are on the
233 questions of the two development conversations and should be read with the run-to-run noise measured in
Section~\ref{sec:results}: plain retrieval, which does not use the extractor at all, moved from 81.1\% to 83.7\%
between the two v6 runs.


\section{\uppercase{Results}}
\label{sec:results}
The test run (\code{locomo-final}, commit \code{fb044f2}) built a memory bank for each of the ten LoCoMo conversations
and answered all 1,540 questions under each condition. Table~\ref{tab:bench-criteria} gives the verdict on the
criteria fixed before the run: the memory engine passes all of them, on all ten conversations and on the eight never
used for diagnosis.

\input{5/tables/criteria}

Table~\ref{tab:bench-main} gives the full results. With the engine the reader answered 83.1\% of the questions
correctly. Without any memory it answered almost none (0.3\%), because LoCoMo asks about details of the
conversation that no model can know. An agent that keeps only its most recent 8,192 tokens, which is what happens
when a long history overflows the context window, answered 43.0\%: the evidence for most questions lies in
earlier sessions. Plain retrieval over the raw text answered 80.0\%, and giving the reader the whole conversation,
about 22,400 tokens, answered 89.0\%. The engine therefore closes most of the gap between plain retrieval and the
whole conversation while giving the reader 30\% of the tokens.

\input{5/tables/main}

Table~\ref{tab:bench-paired-jev} gives the paired differences. The engine is 3.1 points above plain retrieval;
the 95\% interval is [1.2, 4.8] over questions and [2.0, 4.0] over conversations, so the gain is small but not
noise. It is 6.0 points below the whole conversation and 40.1 points above the recent window.
GPT-4o-mini, the second judge, gives the same ordering and nearly the same differences
(Table~\ref{tab:bench-paired-gpt4omini}): 3.1 points above plain retrieval, interval [1.2, 5.0] over questions.

\subsection{Held-out conversations}
All faults in Section~\ref{sec:iterations} were found on conversations 26 and 30, so a gain that came from tuning to
those two would shrink on the rest. Table~\ref{tab:bench-held-out} shows it does not: on the other eight the engine
answers 83.0\% against 79.4\% for plain retrieval and 88.9\% for the whole conversation, the same picture as on
all ten.

\input{5/tables/held-out}

\subsection{Question categories}
Table~\ref{tab:bench-categories} splits the results by category. The engine's advantage over plain retrieval comes
mostly from multi-hop questions (83.0\% against 74.5\%), which need facts from several sessions. Asked ``What
subject have Caroline and Melanie both painted?'', the reader answered ``Nature'' from plain retrieval's chunks; the engine's recall held one assertion per person (``Caroline painted a sunset scene \ldots'' and
``Melanie painted a sunset with a palm tree \ldots''), and the reader answered
``Sunsets''. An assertion states in one sentence what the conversation spread over several turns, so facts from
different sessions fit side by side in the budget. On single-hop questions the engine is 3.1 points ahead. On
temporal and open-domain questions the two are level (80.1\% against 80.4\%, and 58.3\% against 60.4\% on only 96
questions). Temporal questions are where the engine should help most and did not; Section~\ref{sec:properties}
shows why.

\input{5/tables/categories}

\subsection{Ablations}
On the 300-question sample (75 per category), removing the source text from recall (\code{assertions\_only}) costs
9.7 points (interval [4.7, 14.7] over questions), so extracted assertions do not yet replace the text they came from;
they help when given beside it. Removing consolidation costs 1.7 points by Jev and 0.3 by GPT-4o-mini, and removing the graph 0.0 and 0.7; none
of these intervals over questions excludes zero (for consolidation by Jev, [$-$1.3, 4.3]), so on this sample
neither module has a measurable effect on accuracy. LoCoMo's questions are
about two people and rarely need a chain of relations, so this benchmark cannot show what the graph is for; its
role in tracing corrections is checked by the property suite instead.

\subsection{Run-to-run variation and judge agreement}
The reader does not give the same answer every time. On the 300-question sample each condition was asked three
times (Table~\ref{tab:bench-repeats}). The engine's accuracy varied by 0.5 points (standard deviation) between
runs and plain retrieval's by 1.3, while 7 to 8\% of individual verdicts changed in at least one run. Differences
of a point or two on a few hundred questions are therefore within noise, which is why the development-run changes
in Section~\ref{sec:iterations} are read with caution; the 3.1-point gain over plain retrieval on 1,540 questions
is outside it. The two judges agree closely (Table~\ref{tab:bench-judges}): they give the same verdict on 96.7\% of
the 8,600 answers (Cohen's $\kappa$ = 0.93), and no condition's accuracy differs between them by more than 1.0
point.

\section{\uppercase{Performance Analysis}}
\label{sec:performance}
\subsection{Retrieval and provenance}
Table~\ref{tab:bench-retrieval} scores retrieval against LoCoMo's evidence labels, the dialogue turns that answer
each question. The engine and plain retrieval find the right session about equally often (80\% in the top five,
about 97\% somewhere in the packed context), but the engine's context contains the exact evidence turn more often
(84.4\% against 80.6\%), because an assertion carries the quote of the turn it came from even when its own text
ranks the turn low. Assertions alone reach the evidence turn for only 62.2\% of questions, which matches their
lower accuracy: the extractor still misses facts. Every one of the 99,971 source quotes the engine returned
matched the dataset turn it cites exactly, so an answer built from recall can always be traced to what was said.

\input{5/tables/retrieval}

\subsection{Tokens and latency}
The engine gives the reader 6,790 tokens of context per question on average, 30\% of the 22,400 of the whole
conversation; counting the reader's prompt and answer, a question costs 14,900 tokens against 35,300. For LoCoMo's
conversations, about 22,000 tokens each, the whole conversation still fits in Haiku's context window, and the reader
answers it about as fast (5.5 s against 5.2 s at the median) because a hosted model reads input in parallel. The
engine's advantage here is therefore cost and the ability to grow: its context stays within the 8,192-token budget
however long the history becomes, while the whole conversation grows with every session and eventually does not
fit. The engine's own recall takes 428 ms at the median and 584 ms at the 95th percentile, including the query
embedding, so it adds less than a tenth to the reader's time.

\subsection{Cost of building memory}
Building memory is the expensive step (Table~\ref{tab:bench-ingestion}). The ten conversations, 272 sessions and
5,882 turns, took 4.2 hours of wall-clock time on the laptop, four conversations at a time: about 56 seconds of
wall-clock time per session, nearly all of it extraction by the 4B model. No job failed permanently. This cost is paid
once, in the background, when a session is retained; it does not delay the agent's answers. A larger GPU or a
second model slot would shorten it in proportion.

\section{\uppercase{Property Suite}}
\label{sec:properties}
LoCoMo's questions do not separate a current value from an old one, and its judge cannot see the stored state. The
property suite checks those behaviours directly on 40 scripted conversations (Table~\ref{tab:bench-properties}).
Abstention, credential handling and knowledge updates behave as designed: the engine declines to answer without
evidence in all six cases, never stores an API key, and after each of the 12 updates returns the new value first
while \code{as\_of} recall returns the old one. Every source quote is verbatim.

The suite also found a fault the LoCoMo judge could not see. In the test run no relative date was resolved
(0 of 12): the Stage C worker writes the resolved date into the statement, ``Priya plans to run a half marathon on
2025-09-24'', but often leaves the event date empty, and the store then filled it with the time the message was
sent. The reader still answered all 12 date questions correctly from the statement, which is why accuracy did not
reveal it. The engine now resolves a relative day named in the claim's quote when the event date is empty as well
(commit \code{43af5bd}); re-run on the fixed engine (\code{properties-v7}), all 10 extracted events carry the right
date, and the other two were never extracted. The LoCoMo numbers above are for the engine before this fix.

The remaining failures are all facts the extractor did not produce, not facts it got wrong. When a relative moves,
the move is always attributed to the relative and never overwrites the user's city, but in four of six
conversations the user's own city was never extracted; in two of four credential conversations, the ordinary fact
said in the same message as the API key was dropped together with the key; and in two of 12 updates the old value
was not stored as history. This is the same coverage gap the \code{assertions\_only} ablation shows.

\section{\uppercase{Comparison with Existing Systems}}
\label{sec:comparison}
Table~\ref{tab:bench-published} places the result beside the LoCoMo results published with Mem0
\cite{chhikara2025mem0}, which also reports Zep \cite{rasmussen2025zep}, LangMem \cite{langchain2025langmem}, A-Mem
\cite{xu2025amem}, OpenAI's memory and a tuned retrieval baseline, all graded by GPT-4o-mini with the rubric used
here. The absolute scores cannot be compared directly: the published systems answer with GPT-4o-mini and this work
with Claude Haiku 5.5, a stronger reader, which lifts every condition, including the whole-conversation baseline
(88.8\% here against 72.9\% there). The fairer comparison is each system's distance from the whole-conversation
baseline of its own study, the last column. There the engine is 5.6 points behind, against 4.5 points for
Mem0 with its graph, 6.0 for Mem0, 6.9 for Zep and 11.9 for the best retrieval baseline; this work's own plain
retrieval is 8.8 points behind. By this measure the engine is in the same range as Mem0 and Zep, not ahead of
them, and it gives the reader more context to get there (6,790 tokens against 1,764 for Mem0 and 3,911 for Zep). A
stronger reader also leaves less room for memory to help, so the distances are only a rough guide.

\input{5/tables/published}

Beyond accuracy, the engine differs from these systems in what it keeps. Mem0 and A-Mem rewrite or delete a memory
when it is updated; the engine keeps every version with its validity interval and source quote, which is what lets
\code{as\_of} recall answer about the past and lets every answer be traced to a turn of the conversation. It also runs
entirely on one laptop: extraction, consolidation and embedding use a 4B model on an 8 GB GPU, where the published
evaluation called a hosted model for every memory operation.

\section{\uppercase{Threats to Validity}}
\begin{itemize}[itemsep=0pt]
\item \textbf{One benchmark.} LoCoMo has ten conversations between two people; LongMemEval was planned and not run.
Results on other kinds of history, such as an agent's coding sessions, are not measured here.
\item \textbf{Few conversations.} Intervals over conversations rest on ten clusters. With so few, a bootstrap
interval can be too narrow, and here it was sometimes narrower than the interval over questions, so conclusions
are drawn only where both intervals agree.
\item \textbf{Development on the test set.} Faults were diagnosed on two of the ten conversations, and the
test includes them. The eight held-out conversations give the same result.
\item \textbf{Model judges.} Accuracy is decided by two model judges, not people. They agree on 96.7\% of answers
(Cohen's $\kappa$ 0.93), and the notebook prints random items in full for checking by hand.
\item \textbf{Reader.} One reader model was used. A weaker reader may rely more on the memory, a stronger one less.
\item \textbf{Equal budgets.} The engine and plain retrieval share the 8,192-token budget, but plain retrieval used
4,473 tokens of it against 6,790 for the engine, because its chunks ran out of relevant text; giving it more chunks
might narrow the 3.1-point gap.
\item \textbf{Relative dates.} The fault found by the property suite after the test (Section~\ref{sec:properties})
was present in the test run, so the LoCoMo numbers are for the engine before that fix, and the fix is checked
only by the 12 scripted date scenarios.
\end{itemize}

\section{\uppercase{Conclusion and Future Work}}
We built all five modules of the memory engine and measured whether it helps an agent. On LoCoMo, with the same
reader under every condition, the engine raised accuracy from 43.0\% for an agent that keeps only its recent
history, and 80.0\% for plain retrieval over the raw text, to 83.1\%. That is 6.0 points below giving the reader
the whole conversation, while using 30\% of its tokens and a context that does not grow with the history. Every
criterion fixed before the test passed, on all ten conversations and on the eight never used for development; two
judges from different model families agree on 96.7\% of the verdicts; and every one of the 99,971 source quotes
the engine returned matched the conversation exactly. The gain over plain retrieval is small, 3.1 points, and comes
mostly from multi-hop questions. The engine's other properties, which LoCoMo does not measure, were confirmed
directly: corrections keep their history and \code{as\_of} recall returns it, the engine abstains without
evidence, and it never stores a credential.

The results also show what is not yet good enough. Assertions alone answer 66.7\%, far below the source text they
came from, so the extractor still misses facts even after Stage C; the graph and consolidation had no measurable
effect on LoCoMo; and relative dates were wrong in the test run until the fix found by the property suite.
Building memory costs about a minute of GPU time per session on a laptop. Future work, by module:
\begin{itemize}[itemsep=0pt]
\item M1: API access control and verified backup and restore.
\item M2: better extraction coverage, so that assertions can replace more of the source text in the budget, and
faster extraction.
\item M3: evaluate ambiguous updates, aliases and longer correction histories on a benchmark built for them.
\item M4: run LongMemEval and an agent-coding benchmark, and test whether the graph helps on histories with more
people and relations than LoCoMo has.
\item M5: more coverage-focused training, a date-resolution test set, and independent human review of the judges.
\end{itemize}
